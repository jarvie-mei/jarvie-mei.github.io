Some simple customizations and performance improvements for my blog site

I've always wanted to maintain a personal blog, and I finally found a Hugo theme that I really liked. After spending a day or two customizing it, adding a few features, and experimenting with different performance improvements, I decided to document what I changed and why.

This blog is hosted on GitHub Pages, which is simple, reliable, and more than enough for a static site. However, GitHub Pages alone is not always ideal when it comes to resource loading speed, especially for visitors from different network environments.

So I made a number of small improvements around Cloudflare, caching, analytics, and browser-side performance.

TL;DR

The main changes include:

  • Serving most static assets such as CSS, JavaScript, and images through a CDN

  • Adding simple traffic routing for users in different regions

  • Using Cloudflare R2 as the image hosting backend

  • Proxying Google Analytics 4 through Cloudflare Workers

  • Adding Quicklink to speed up navigation between pages

  • Making several smaller optimizations based on Lighthouse and other performance recommendations

None of these changes are particularly complicated on their own, but together they noticeably improve the overall experience of the blog.

1. GitHub Pages as the Hosting Platform

The blog itself is still hosted on GitHub Pages.

For a personal static blog, GitHub Pages has several advantages:

  • free hosting

  • easy integration with Git

  • simple deployment through GitHub Actions

  • no server maintenance

  • good reliability

I also prefer keeping the deployment architecture as simple as possible.

Rather than moving the entire website behind another hosting platform, I keep GitHub Pages as the origin and use other services only where they provide a clear benefit.

In other words, the architecture roughly looks like this:

Git Repository
      │
      ▼
GitHub Actions
      │
      ▼
GitHub Pages
      │
      ├── HTML pages
      │
      └── static resources
                │
                ▼
        CDN / Cloudflare

This gives me the simplicity of GitHub Pages while still allowing some flexibility around static assets.

2. Accelerating Static Resources with a CDN

A Github Pages site is mostly made up of static files:

HTML
CSS
JavaScript
images
fonts

HTML documents are relatively small, but CSS, JavaScript, fonts, and especially images can account for a large portion of the total transferred data.

Instead of serving every resource directly from the GitHub Pages domain, I moved most reusable static assets behind a CDN.

For example, the original URLs may look like:

https://example.github.io/css/style.min.css
https://example.github.io/js/main.js

while the optimized versions can be served through a CDN domain:

https://cdn.example.com/css/style.min.css
https://cdn.example.com/js/main.js

This also makes it easier to control caching policies independently from the main website.

Cloudflare

Cloudflare (hereafter referred to as CF) is probably the most generous cloud provider I know of. In addition to offering free CDN services, it also provides a wide range of other cloud services with generous free tiers, making it a great platform for experimentation.

Over the past few days, I only spent a little time reproducing a few setups that can improve my blog's performance at no cost, and even that was enough to make me realize just how much there is to explore within the Cloudflare ecosystem.

Static Files Acceleration

Before going further, I would like to briefly introduce the current architecture of my blog:

  • I only use jarvie-mei.github.io as the primary domain. Since I no longer plan to maintain a separate custom domain for the blog, my setup is different from many other blogs: I do not put the main blog domain directly behind Cloudflare for acceleration.
  • Instead, I use another domain hosted on Cloudflare specifically for acceleration purposes. The main focus is on static assets, which can generally be divided into CSS, JavaScript, and image resources.
    • CSS and JavaScript assets can be accelerated directly through third-party CDN services such as jsDelivr.
      • Some resources require special handling. Google Fonts, for example, may need to be proxied, served through another CDN, or replaced with an alternative such as Cloudflare Fonts.
    • Image hosting can be handled separately depending on the expected network environment of the blog's readers. Different cloud providers offer both free and paid storage solutions. Another simple option is to store images on GitHub and serve them through jsDelivr.

One point worth mentioning is that some blog posts suggest that putting CSS, JavaScript, and other static resources behind Cloudflare can sometimes have the opposite effect and actually make things slower.

After some testing, I found that putting these static assets behind the CDN actually made the initial request slower.

The main reason is that my current setup does not serve the resource directly from Cloudflare. Instead, the browser first requests my custom CDN domain, which then redirects the request to jsDelivr or jsDMirror based on the visitor's region.

The request flow looks roughly like this:

Browser
  ↓
cdn.mjtech.top
  ↓
Cloudflare
  ↓
302 Redirect
  ↓
cdn.jsdelivr.net / cdn.jsdmirror.com
  ↓
200 Response

Compared with accessing GitHub Pages directly, this introduces an extra HTTP redirect and may also require another DNS lookup, TCP connection, and TLS handshake.

For small CSS and JavaScript files, the actual file transfer time is already very short, so the additional network round trips can outweigh the performance benefit provided by the CDN.

Another factor is that GitHub Pages already uses its own edge delivery infrastructure, while jsDelivr itself is a multi-CDN service. Adding an extra Cloudflare-based geo-routing layer therefore does not necessarily reduce latency further.

However, this additional overhead mainly affects the first request. With a Service Worker and Workbox caching enabled, subsequent visits can often be served directly from the browser cache without going through the full 302 → CDN → 200 request chain again.

So, in this setup, Cloudflare is better thought of as a geo-based CDN router rather than an additional acceleration layer that is guaranteed to make every request faster.

Traffic Diversion

  1. First, host your domain on Cloudflare and add a CNAME record pointing to cdn.jsdmirror.com, with the proxy status enabled. In the following examples, we will use cdn.mjtech.top.

  2. Rule 1: This rule is mainly used to route traffic from mainland China. Use a custom filter expression and configure it as shown in the screenshot. Set the hostname to cdn.zdy.one, which is the domain configured earlier, and set the country/region to China. For the redirect target, use:

    concat("https://cdn.jsdmirror.com", http.request.uri.path)

  3. Rule 2: This rule is mainly used to route traffic from outside mainland China. The configuration is similar to Rule 1, except that the country/region condition should be set to not equal to China. Change the redirect expression to:

    concat("https://cdn.jsdelivr.net", http.request.uri.path)

The resources I mainly moved behind the CDN were:

CSS
JavaScript
avatar images
article images
search scripts
other theme assets

One important thing to keep in mind when loading JavaScript from third-party CDN endpoints is Subresource Integrity, or SRI.

Whenever possible, externally hosted scripts should include an integrity hash so that the browser can verify that the downloaded resource has not been unexpectedly modified.

3. Simple Regional Traffic Routing

A single CDN provider does not necessarily perform equally well from every network.

Since the blog may be visited from both mainland China and other regions, I experimented with simple regional routing.

The basic idea is:

                    ┌── CDN A
Visitor ──> CDN Domain
                    └── CDN B

Instead of forcing every visitor to use the same upstream provider, requests can be routed differently depending on their region.

For example:

Mainland China
      │
      ▼
Alternative CDN endpoint

Other regions
      │
      ▼
Global CDN endpoint

Cloudflare's rules and Workers make this kind of architecture relatively easy to experiment with.

I do not consider this a perfect global traffic management solution. It is simply a lightweight optimization for a personal blog.

The important principle is not to assume that one CDN will always be the fastest everywhere.

Actual network performance should be measured from the environments that matter to your readers.

4. Using Cloudflare R2 as an Image Host

Full tutorial can be found here1

Images are usually the largest static resources on a blog.

Previously, I considered several approaches:

GitHub repository
third-party image hosting
traditional object storage
S3-compatible storage
Cloudflare R2

I eventually chose Cloudflare R2.

For a personal blog, R2 is convenient because it gives me an object-storage model while integrating naturally with the rest of the Cloudflare ecosystem.

My image pipeline is roughly:

Local image
    │
    ▼
Image uploader
    │
    ▼
Cloudflare R2
    │
    ▼
Custom image domain
    │
    ▼
Blog article

This also keeps large images out of the main Git repository.

Cache Images Aggressively

Blog images rarely change after publication.

Because of that, they are good candidates for long cache lifetimes.

A typical cache policy can look like:

Browser Cache
      │
      ▼
Cloudflare Edge Cache
      │
      ▼
R2 Object Storage

For immutable images, long TTL values can significantly reduce repeated requests to the origin.

Of course, long caching also means that replacing an existing file under the exact same URL becomes more difficult.

A better solution is to use versioned or content-based filenames:

diagram-a82f3c.webp
photo-2026-09.webp

instead of repeatedly overwriting:

image.webp

5. Using Fewer Images

One optimization that does not require any technology is simply using fewer unnecessary images.

When writing technical articles, it is tempting to include screenshots for almost every step.

But many screenshots do not actually add useful information.

For example, if one sentence can clearly explain the result:

The command returned the expected flag.

then a full screenshot showing the exact same thing may not provide much additional value.

Now I try to divide images into roughly three categories:

Essential
The article becomes difficult to understand without it.

Useful
The image makes the explanation easier to follow.

Decorative
Removing the image has almost no effect on understanding.

Essential images deserve reliable storage and long-term hosting.

Decorative screenshots usually do not.

This reduces page size and also makes articles easier to maintain.

6. Proxying Google Analytics 4 with Cloudflare Workers

Google Analytics is useful for understanding basic traffic patterns, but directly loading analytics resources can introduce a few problems.

For example:

  • additional third-party requests

  • network availability differences

  • scripts being blocked by browser extensions

  • additional JavaScript overhead

Since I was already using Cloudflare, I experimented with putting a Worker in front of the analytics requests.

The architecture becomes:

Browser
   │
   ▼
Cloudflare Worker
   │
   ▼
Google Analytics

Instead of having the browser communicate directly with Google's endpoint for every analytics-related request, the Worker acts as a small reverse proxy.

This also gives me more control over how those requests are handled.

The Worker can be exposed through a custom subdomain such as:

analytics.example.com

and the frontend can send analytics requests through that endpoint.

I also prefer keeping the analytics script as lightweight as possible.

For a small personal blog, I do not need a large analytics framework running on every page if a much smaller implementation can provide the metrics I actually care about.

7. Improving Service Worker Caching with Workbox

I had already experimented with Service Workers before, but I revisited the configuration and updated the caching strategy with Workbox.

A Service Worker sits between the browser and the network:

Browser
   │
   ▼
Service Worker
   │
   ├── Cache
   │
   └── Network

This makes it possible to control how resources are retrieved.

Different resources benefit from different strategies.

For example:

HTML
Network First

CSS / JavaScript
Stale While Revalidate

Images
Cache First

Frequently changing API data
Network First

There is no single caching strategy that works best for everything.

Stale While Revalidate

For static theme resources, StaleWhileRevalidate is particularly useful.

The browser can immediately use the cached resource while the Service Worker checks for an updated version in the background.

Conceptually:

Request
   │
   ├── cached version ──> return immediately
   │
   └── network request ──> update cache

This provides a good balance between performance and freshness.

Precaching

Workbox also supports precaching.

Precaching means downloading a known set of resources while the Service Worker is being installed.

For example:

Service Worker installation
          │
          ▼
precache important resources
          │
          ▼
ready for future navigation

This can be useful for resources that are always required.

However, I do not try to precache everything.

Over-aggressive precaching can easily waste bandwidth and storage, especially when many resources are already efficiently delivered through a CDN.

Caching should reduce unnecessary work, not create more of it.

8. Faster Navigation with Quicklink

Another interesting optimization is predicting which page the visitor is likely to open next.

Normally, clicking a link works like this:

click
  │
  ▼
request page
  │
  ▼
download
  │
  ▼
render

But the browser often has enough idle time before the user actually clicks.

If a likely navigation target can be prefetched beforehand, the process becomes:

link becomes likely to be clicked
            │
            ▼
         prefetch
            │
            ▼
          cache

        user clicks
            │
            ▼
       page available

This can make navigation feel almost instantaneous.

I initially looked into the browser's Speculation Rules API, which provides native mechanisms for prefetching and prerendering future navigation targets.

However, for my blog I wanted something simpler to integrate.

So I used Quicklink.

A minimal setup looks like this:

<script
  src="https://cdn.jsdelivr.net/npm/quicklink@2.3.0/dist/quicklink.umd.js"
  defer>
</script>

<script>
window.addEventListener("load", () => {
  quicklink.listen();
});
</script>

Quicklink observes links on the page and uses browser idle time to prefetch likely navigation targets.

For a static multi-page blog, this is especially useful because most navigation consists of moving between regular HTML documents.

For example:

Home
 ├── Article A
 ├── Article B
 ├── Archives
 ├── About
 └── Tags

These pages are excellent candidates for lightweight prefetching.

Of course, prefetching should still be used carefully.

Downloading every possible destination aggressively can waste bandwidth, especially for users on mobile networks.

The goal is to make navigation smarter, not simply download the entire website in advance.

9. Speculation Rules API

Modern browsers are also introducing the Speculation Rules API.

It allows a page to describe which future navigations should be:

prefetched
or
prerendered

Prefetching downloads the document before it is needed.

Prerendering goes further and prepares the page in the background so that navigation can happen almost instantly.

Conceptually:

Current Page

    │
    ├── likely next page
    │       │
    │       ▼
    │    prefetch
    │
    └── highly likely next page
            │
            ▼
        prerender

This is particularly interesting for multi-page applications and static sites such as Hugo blogs.

For now, I still prefer the simplicity of Quicklink for my own site, but the Speculation Rules API is definitely something worth following as browser support continues to improve.

10. Smaller Theme Optimizations

Besides the larger changes above, I also made several smaller improvements to the original Hugo theme.

These were mostly based on browser developer tools and performance audits.

Convert Images to Modern Formats

PNG is useful when lossless quality or transparency is required, but it is often much larger than necessary.

For assets such as avatars and screenshots, formats such as:

WebP
AVIF

can significantly reduce file size.

For example:

avatar.png
     ↓
avatar.webp

A tiny optimization by itself, but these savings add up across a website.

Defer Non-Critical JavaScript

JavaScript that is not required for the initial render should usually avoid blocking the HTML parser.

For example:

<script src="/js/search.js" defer></script>

The browser can continue parsing the document while the script downloads.

This is useful for functionality such as:

search
analytics
image galleries
optional UI effects
prefetch logic

that does not need to execute before the first visible content appears.

Avoid Unnecessary JavaScript

One of the easiest ways to improve a static website is simply to ship less JavaScript.

Hugo already generates static HTML, so most content does not require JavaScript at all.

Whenever I add a new feature, I try to ask:

Does this actually require JavaScript?

If CSS or native browser functionality can solve the problem, that is usually preferable.

11. Measuring Performance

Performance optimization should be based on measurements rather than intuition.

I mainly use tools such as:

Chrome DevTools
Lighthouse
PageSpeed Insights
WebPageTest

They can reveal problems including:

render-blocking resources
large images
unused JavaScript
poor caching policies
layout shifts
slow server responses
font loading issues

However, performance scores should not become the goal themselves.

A Lighthouse score of 100 does not automatically mean a website provides a better experience.

Sometimes an optimization recommended by an automated tool can conflict with:

readability
maintainability
compatibility
visual quality
functionality

So I treat these tools as diagnostic tools rather than absolute rules.

The real goal is not:

maximize the performance score

but rather:

make the site feel fast and reliable for actual visitors

But experimenting with these technologies is also part of the fun.

Conclusion

None of the optimizations described here are revolutionary.

Most of them are relatively small improvements:

CDN caching
regional routing
object storage
Service Worker caching
prefetching
smaller images
deferred scripts
lighter analytics

But web performance is often the result of many small improvements rather than one dramatic change.

More importantly, working on the blog gave me an opportunity to explore technologies that I normally would not use in such a small project, including Cloudflare Workers, R2, Workbox, browser caching strategies, prefetching, and newer browser APIs.

There are still plenty of things that could be improved, and I will probably continue adjusting the setup as the blog evolves.

For now, though, I am fairly happy with the result.

And hopefully, after spending this much time optimizing the blog itself, I can finally spend more time actually writing posts.
